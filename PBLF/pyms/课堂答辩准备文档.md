## 1. 项目概述

**项目名称：** PyMS（Python Web Crawler Console）

**核心功能：** 一个基于 Web 的爬虫控制台，用户通过浏览器输入 URL，系统自动完成网页爬取 → 数据清洗 → 词云生成 → 情感分析的全流程，支持"一键执行"。

**技术栈：**
- 后端框架：Sanic（异步 Web 框架）
- 数据库：SQLite
- 爬虫：Requests + BeautifulSoup4
- 中文分词：jieba
- 词云生成：wordcloud
- 情感分析：snownlp（Senta 模型）
- 前端：原生 HTML/CSS/JavaScript（单页应用）
- 测试：unittest + sanic-testing

### 3.2 一键执行的完整数据流

```
步骤1: 用户在浏览器输入 URL，点击"开始"
        │
        ▼
步骤2: 前端 POST /v1/crawl/submit
        ├─ 参数: url, limit(默认50), depth(默认1), keyword(可选)
        │
        ▼
步骤3: service.submit_task()
        ├─ validate_target_url() 安全校验
        ├─ 在 tasks 表创建记录，状态=pending
        ├─ 在 queue_items 表插入初始 URL
        └─ 在 event_logs 记录 task_created 事件
        │
        ▼
步骤4: 前端执行命令 "crawl start url=... task_id=..."
        └─ command_engine → transition_task(task_id, "running")
        │
        ▼
步骤5: QueueRunner 后台线程（持续轮询）
        ├─ _fetch_pending_items(): 批量取 pending 状态的队列项
        ├─ 使用 ThreadPoolExecutor（最大4线程）并发处理
        └─ _process_item() → default_fetch_url(url)
        │
        ▼
步骤6: 爬虫抓取
        ├─ requests.get(url) 获取 HTML
        ├─ BeautifulSoup 解析: 提取 title, <p>正文, <a>链接
        ├─ 保存原始数据到 raw_items 表
        └─ 如果 hop_count < depth，将新发现的 URL 加入队列
        │
        ▼
步骤7: 关键字过滤（如果设置了 keyword）
        ├─ _match_keyword(): 逗号分隔多关键字，不区分大小写
        └─ 只保存标题或内容包含关键字的页面
        │
        ▼
步骤8: 任务完成判定
        ├─ _finalize_if_done(): 检查是否所有队列项都处理完毕
        ├─ done_count > 0 → success
        └─ done_count == 0 且 failed_count > 0 → failed
        │
        ▼
步骤9: 前端检测到任务完成（轮询任务状态，2秒/次）
        └─ 执行命令 "clean run task_id=..."
        │
        ▼
步骤10: 数据清洗 (cleaning.py)
        ├─ _normalize_text(): 去除 HTML 标签，合并空白字符
        ├─ _normalize_date(): 统一日期格式为 YYYY-MM-DD
        ├─ _build_dedup_key(): 生成去重键（news_id 或 SHA1(title+date)）
        └─ INSERT OR IGNORE 实现自动去重
        │
        ▼
步骤11: 前端执行命令 "wordcloud run task_id=..."
        │
        ▼
步骤12: 词云 + 情感分析
        ├─ jieba.cut() 中文分词，过滤停用词和单字词
        ├─ WordCloud 生成 800×400 PNG 图片
        ├─ 自动查找系统中文字体（微软雅黑/黑体/宋体/PingFang）
        ├─ snownlp.SnowNLP.sentiments 计算情感得分
        │   ├─ score > 0.6 → 正面
        │   ├─ score < 0.4 → 负面
        │   └─ 0.4 ≤ score ≤ 0.6 → 中立
        └─ 返回 base64 编码的 PNG + 情感统计 JSON
        │
        ▼
步骤13: 前端渲染
        ├─ 显示词云图片（data:image/png;base64,...）
        └─ 显示情感分析柱状图（正面/中立/负面）
```

### 3.3 任务状态机

```
          ┌─────────┐
          │ pending  │  ← 创建任务后的初始状态
          └────┬─────┘
               │ (启动)
               ▼
          ┌─────────┐
     ┌────│ running  │────┐────┐
     │    └─────────┘    │    │
     │         │         │    │
  (恢复)    (暂停)     (停止)  (完成/失败)
     │         │         │    │
     ▼         ▼         ▼    ▼
  running   paused    stopped  success / failed
              │                  ↑
              │ (停止)           │
              ▼                  │
           stopped         终态（不可再迁移）
```

**状态说明：**
- `pending`：任务已创建，等待 Worker 处理
- `running`：Worker 正在抓取
- `paused`：暂停，队列项重置为 pending，恢复后继续
- `stopped`：用户手动停止，未完成的队列项标记为 canceled
- `success`：至少有一个页面成功抓取
- `failed`：所有页面都失败

### 3.4 前端一键执行流程

前端 `app.js` 中的 `startOneClick(url)` 函数：

```
1. 显示进度条（4个步骤指示器）
2. POST /v1/crawl/submit → 获取 task_id
3. 等待 1 秒
4. POST /v1/command "crawl start ..." → 启动爬虫
5. 轮询 GET /v1/tasks/{id}（每2秒，最长5分钟）
6. 任务完成 → POST /v1/command "clean run ..."
7. 等待 1 秒
8. POST /v1/command "wordcloud run ..."
9. 显示词云图片和情感分析结果
10. 更新进度条为完成状态
```

## 4. 核心技术细节

### 4.1 SSRF 防护机制

```python
# security.py 核心逻辑
def validate_target_url(url: str) -> str:
    # 1. 只允许 http/https 协议
    # 2. 必须有 hostname
    # 3. 禁止 localhost
    # 4. 禁止私有 IP (10.x, 172.16-31.x, 192.168.x)
    # 5. 禁止回环地址 (127.x)
    # 6. 禁止链路本地地址 (169.254.x)
```

**为什么需要：** 防止攻击者利用爬虫访问内网服务（如数据库管理面板、内部 API），这是典型的 SSRF（Server-Side Request Forgery）漏洞。

### 4.2 并发爬取模型

```
QueueRunner（守护线程，持续运行）
    │
    ├─ 每 0.1 秒轮询一次数据库
    ├─ 批量获取最多 MAX_WORKERS(4) 个 pending 项
    ├─ 使用 CAS（Compare-And-Swap）避免并发冲突：
    │   UPDATE ... WHERE id = ? AND state = 'pending'
    │   只有 rowcount > 0 才表示成功获取
    └─ ThreadPoolExecutor（4个工作线程）并发抓取
```

**关键设计：**
- 使用 `threading.Event` 实现唤醒机制，避免忙等待
- `_session_lock` 保护全局 `requests.Session`（TCP 连接复用）
- 每个抓取任务都有 8 秒超时

### 4.3 去重策略

```python
# cleaning.py 中的去重机制
def _build_dedup_key(news_id, title, date):
    if news_id:
        return f"news_id:{news_id}"      # 优先用 news_id
    source = f"{title or ''}|{date or ''}"
    return "title_date:" + hashlib.sha1(source.encode()).hexdigest()  # 备选: SHA1
```

```python
def _senta_score(text: str) -> float:
    from snownlp import SnowNLP
    # 清理特殊字符（防止编码错误）
    cleaned = ''.join(c for c in text if ord(c) < 0x10000)
    s = SnowNLP(cleaned)
```

### 5.2 关键表字段说明

**tasks 表：**
- `task_id`：格式为 `task_` + UUID 前12位（如 `task_a1b2c3d4e5f6`）
- `status`：枚举值 `pending/running/paused/stopped/success/failed`
- `total_count`：队列总数（初始为1，爬取过程中动态增加）
- `done_count` + `failed_count`：用于计算进度百分比

**queue_items 表：**
- `UNIQUE(task_id, url)`：同一任务中同一 URL 不会重复入队
- `hop_count`：当前 URL 距离根 URL 的跳数（用于深度控制）
- `state`：`pending/running/done/failed/canceled`
- `priority`：默认 100，用于排序

**clean_items 表：**
- `UNIQUE(task_id, dedup_key)`：配合 `INSERT OR IGNORE` 实现去重
- `dedup_key`：`news_id:xxx` 或 `title_date:` + SHA1 哈希

## 6. 关键代码解析

### 6.1 Worker 中的 CAS 并发控制

```python
# worker.py - _fetch_pending_items()
# 使用 SQL 的 WHERE 条件实现 CAS，避免多线程重复处理同一条记录
updated = conn.execute(
    "UPDATE queue_items SET state = 'running', updated_at = ? "
    "WHERE id = ? AND state = 'pending'",
    (now, row["id"]),
)
if updated.rowcount > 0:  # 只有实际更新成功才加入处理列表
    items.append(dict(row))
```

### 6.2 深度优先的 URL 发现

```python
# worker.py - _enqueue_links()
# 只有 hop_count < max_depth 时才将新 URL 入队
if hop_count < max_depth:
    _enqueue_links(conn, task_id, url, hop_count + 1, limit_count, discovered_urls, now)

# 限制队列总数不超过 limit_count
count = conn.execute("SELECT COUNT(*) FROM queue_items WHERE task_id = ?", (task_id,)).fetchone()["c"]
for url in urls:
    if count >= limit_count:
        break
```

### 6.3 暂停/恢复的实现细节

```python
# service.py - transition_task()
# 暂停时：将 running 状态的队列项重置为 pending
if target == TaskStatus.PAUSED:
    conn.execute(
        "UPDATE queue_items SET state = 'pending' "
        "WHERE task_id = ? AND state = 'running'", (now, task_id))

# 恢复时：通知 Worker 线程
if target == TaskStatus.RUNNING:
    notify_queue_runner()
```

### Q1: 请简要介绍你们的项目做了什么？

**参考回答：**
我们做了一个基于 Python Sanic 框架的 Web 爬虫控制台系统 PyMS。用户在浏览器中输入一个 URL，系统可以自动完成四个步骤：第一，爬取网页内容并解析出标题和正文；第二，对爬取的数据进行清洗和去重；第三，使用 jieba 分词生成词云图；第四，使用 snownlp 的 Senta 模型进行情感分析。整个流程支持一键执行，用户只需点击一个按钮就能看到最终结果。同时系统还支持任务的暂停、恢复、停止，以及数据的 JSON/CSV 导出功能。

---

### Q2: 为什么选择 Sanic 框架而不是 Flask 或 Django？

**参考回答：**
选择 Sanic 主要有三个原因：第一，Sanic 是异步框架，基于 asyncio，天然适合处理 I/O 密集型任务（如网络爬取），能更好地处理并发请求；第二，Sanic 原生支持 SSE（Server-Sent Events），可以实现实时的事件推送，这对我们的爬虫进度展示非常重要；第三，Sanic 的 API 设计简洁，学习曲线平缓，适合我们这个项目规模。相比 Django 太重，Flask 的异步支持不如 Sanic 原生。

---

### Q3: 你们的爬虫是如何实现并发的？为什么不用 asyncio？

**参考回答：**
我们的爬虫采用"后台守护线程 + 线程池"的并发模型。具体来说，有一个 `QueueRunner` 守护线程持续轮询数据库中的待处理队列项，然后使用 `ThreadPoolExecutor`（最大4个工作线程）并发执行 HTTP 请求和 HTML 解析。

没有直接用 asyncio 的原因是：我们使用的 `requests` 库是同步的，不支持 asyncio。如果要完全异步需要换成 `aiohttp`，但考虑到项目的时间限制和 `requests` 的稳定性，我们选择了线程池方案。实际上对于爬虫这种 I/O 密集型任务，线程池已经能提供足够的并发性能。

---

### Q4: 如何防止多线程同时处理同一个 URL（并发冲突问题）？

**参考回答：**
我们使用了数据库层面的 CAS（Compare-And-Swap）机制来解决这个问题。具体做法是：在获取待处理队列项时，不是先 SELECT 再 UPDATE，而是直接执行一个带 WHERE 条件的 UPDATE 语句：

```sql
UPDATE queue_items SET state = 'running' 
WHERE id = ? AND state = 'pending'
```

只有当 `rowcount > 0` 时，才表示成功获取了这条记录。这样即使多个线程同时尝试获取同一条记录，也只有一个能成功，其他的会因为 state 已经变成 'running' 而跳过。这比加锁更轻量，也避免了死锁问题。

### Q5: 任务状态机是怎么设计的？为什么要用状态机？

**参考回答：**
我们定义了 6 种任务状态：pending（待处理）、running（运行中）、paused（暂停）、stopped（已停止）、success（成功）、failed（失败）。每种状态只能迁移到特定的目标状态，比如 running 可以迁移到 paused、stopped、success 或 failed，但不能直接回到 pending。

使用状态机的好处是：第一，明确约束了合法的状态转换，防止程序进入非法状态（比如一个已经成功的任务不能被暂停）；第二，代码逻辑清晰，`can_transition()` 函数用一个字典就能判断转换是否合法；第三，便于扩展，如果将来需要增加新状态，只需修改 `TRANSITIONS` 字典。

### Q6: 你们做了哪些安全防护？

**参考回答：**
我们主要做了两方面的安全防护：

**第一，SSRF 防护。** 爬虫本质上是让服务器去访问用户指定的 URL，如果不做限制，攻击者可能利用这个功能访问内网服务（比如数据库管理页面）。我们在 `security.py` 中实现了 URL 校验：只允许 http/https 协议，禁止 localhost，禁止私有 IP 地址段（10.x、172.16-31.x、192.168.x），禁止回环地址和链路本地地址。

**第二，API Key 认证。** 通过环境变量 `PYMS_API_KEY` 配置，启用后所有 `/v1/` 开头的 API 都需要提供正确的 API Key，支持 Bearer Token、X-API-Key 请求头和 URL 参数三种方式。

### Q7: 数据清洗和去重是怎么做的？

**参考回答：**
数据清洗分三个步骤：

**文本规范化：** 使用 BeautifulSoup 的 `get_text()` 去除 HTML 标签，用正则表达式 `\s+` 合并多余的空白字符。

**日期规范化：** 支持四种日期格式（YYYY-MM-DD、YYYY/MM/DD、YYYY.MM.DD、YYYY年M月D日），统一转换为 YYYY-MM-DD 格式。

**去重：** 采用两层去重策略。优先使用 `news_id` 作为去重键，如果没有 news_id，则用 SHA1 哈希(title + "|" + date) 生成去重键。数据库的 `clean_items` 表对 `(task_id, dedup_key)` 设置了 UNIQUE 约束，配合 `INSERT OR IGNORE` 实现自动去重。

### Q8: 词云生成和情感分析用的什么技术？有什么细节？

**参考回答：**

**词云生成：** 使用 `jieba` 库进行中文分词（精确模式），然后过滤掉停用词（如"的"、"了"、"在"等 25 个常见虚词）和单字词。使用 `wordcloud` 库生成 800×400 像素的 PNG 图片，最大显示 100 个词。一个关键细节是中文字体的处理——词云库默认不支持中文，我们实现了自动检测系统中文字体的逻辑，按优先级查找微软雅黑、黑体、宋体等。

**情感分析：** 使用 `snownlp` 库的 Senta 情感模型。对每条清洗后的文本计算情感得分（0 到 1 之间），大于 0.6 判定为正面，小于 0.4 判定为负面，中间为中立。一个细节是我们在计算前会清理特殊字符（如 emoji），防止编码错误导致分析失败。

### Q9: SSE 和 WebSocket 有什么区别？为什么选 SSE？

**参考回答：**
SSE（Server-Sent Events）是单向的服务器向客户端推送，基于 HTTP 协议；WebSocket 是双向通信，需要独立的连接升级。

选择 SSE 的原因是：我们的场景只需要服务器向客户端推送事件（爬虫进度、任务状态变化），不需要客户端向服务器发送实时数据，所以 SSE 的单向推送模型完全够用。SSE 的优势在于：实现简单（就是一个 `text/event-stream` 的 HTTP 响应）、自动重连（浏览器原生支持 EventSource API）、兼容性好（基于标准 HTTP）。

### Q12: 一键执行的流程是怎样的？如果中间某一步失败了怎么办？

**参考回答：**
一键执行的流程是：提交任务 → 启动爬虫 → 等待爬取完成 → 数据清洗 → 生成词云+情感分析 → 显示结果。

前端通过轮询任务状态来检测每一步是否完成（每 2 秒查询一次，最长等待 5 分钟）。如果爬取失败（比如目标网站不可达），任务状态会变为 `failed`，前端会停止后续步骤并显示错误信息。如果清洗或词云生成失败，命令引擎会抛出 `AppError`，前端捕获错误后显示具体的错误码和错误信息。整个流程有完善的错误处理链，任何一步的异常都不会导致整个系统崩溃。

### Q13: `INSERT OR IGNORE` 是怎么实现去重的？

**参考回答：**
这是利用了 SQLite 的 UNIQUE 约束机制。`clean_items` 表对 `(task_id, dedup_key)` 设置了联合唯一约束。当我们执行 `INSERT OR IGNORE INTO clean_items ...` 时，如果插入的 `(task_id, dedup_key)` 组合已经存在，SQLite 会忽略这条 INSERT 语句而不是报错。`dedup_key` 的生成规则保证了内容相同的记录会有相同的 key：优先用 `news_id`，没有的话用 `SHA1(title + "|" + date)`。这样就实现了数据库层面的自动去重，不需要额外的查询和判断逻辑。

### Q15: 为什么用 SQLite 而不是 MySQL/PostgreSQL？

**参考回答：**
选择 SQLite 主要考虑以下因素：第一，SQLite 是嵌入式数据库，不需要额外安装和配置数据库服务，部署简单；第二，Python 标准库自带 `sqlite3` 模块，零额外依赖；第三，我们的项目是单机部署、单用户场景，不需要 MySQL 那样的高并发支持；第四，SQLite 的性能对于我们的数据量（单任务最多 1000 条记录）完全足够。如果将来需要支持多用户并发，可以很方便地迁移到 PostgreSQL，因为 SQL 语法基本兼容。

### Q16: 命令引擎的设计思路是什么？为什么不直接用 REST API？

**参考回答：**
命令引擎并不是替代 REST API，而是在 REST API 之上提供了一个更灵活的交互方式。前端页面同时支持两种操作方式：直接调用 REST API（比如创建任务、查询结果）和通过命令引擎执行操作（比如 `crawl start`、`clean run`）。

命令引擎的好处是：第一，它提供了一个类似 Shell 的命令行界面，用户可以在控制台中直接输入命令，对调试和高级操作很友好；第二，命令格式统一，便于记录和审计（所有命令都记录到 `command_logs` 表）；第三，它将命令解析和业务逻辑解耦，新增命令只需在 `execute_command()` 中添加一个分支。

### Q17: 你们项目的扩展性如何？如果要支持分布式爬虫，需要改哪些地方？

**参考回答：**
当前架构是单机版，但设计上已经为扩展预留了空间：

**主要修改点：** `worker.py` 的队列获取逻辑、`db.py` 的数据库连接方式、以及需要增加一个分布式锁机制替代当前的 CAS 方案。

### Q18: `hop_count` 和 `depth` 分别是什么意思？它们是怎么配合工作的？

**参考回答：**
`depth` 是用户设置的最大爬取深度，比如设为 2 表示最多从根 URL 向外爬取 2 层链接。`hop_count` 记录的是当前 URL 距离根 URL 的跳数，根 URL 的 `hop_count` 为 0。

配合逻辑是：当一个页面爬取完成后，如果 `hop_count < depth`，就会把这个页面中发现的新 URL 加入队列，新 URL 的 `hop_count` 为当前值加 1。如果 `hop_count >= depth`，就不再继续发现新链接。这样就实现了广度优先的层级爬取控制，防止爬虫无限扩散。

比如设置 `depth=2`：
- 第 0 层：用户输入的根 URL（hop_count=0），会发现新链接
- 第 1 层：根页面中的链接（hop_count=1），会发现新链接
- 第 2 层：第二层页面中的链接（hop_count=2），不再发现新链接

### Q19: 你们是怎么处理爬取失败的情况的？

**参考回答：**
爬取失败的处理分几个层面：

**单个 URL 失败：** 在 `_process_item()` 中捕获异常，调用 `_mark_failed()` 将队列项状态设为 `failed`，记录错误信息到 `last_error` 字段，增加 `failed_count`，然后继续处理其他 URL。一个 URL 的失败不会影响整个任务。

**任务级判定：** 在 `_finalize_if_done()` 中检查，如果所有队列项都处理完毕，且 `done_count == 0`（没有任何成功），则将任务标记为 `failed`；只要有至少一个成功，就标记为 `success`。

**进度计算：** 进度百分比 = `(done_count + failed_count) / total_count * 100`，失败的也算已处理，所以进度条最终会到达 100%。

### Q20: 你们项目的不足之处和改进方向是什么？

**参考回答：**
目前的不足和改进方向有：

1. **爬虫能力有限：** 当前只支持静态 HTML 页面，对于 JavaScript 渲染的页面（如 SPA 应用）无法抓取。可以集成 Selenium 或 Playwright 来支持动态页面。

2. **反爬措施不足：** 没有实现 IP 代理池、请求频率限制、Cookie 管理等反反爬策略。对于有反爬机制的网站可能会被封禁。

4. **前端体验：** 前端是原生 JS 实现的，没有使用前端框架。可以考虑用 Vue/React 重构，提升用户体验。

5. **数据存储：** SQLite 不适合高并发场景，且数据量有限。可以迁移到 PostgreSQL。

6. **情感分析精度：** snownlp 的 Senta 模型相对简单，对于复杂语境的情感判断可能不准确。可以接入更先进的 NLP 模型。

### Q21: 中间件（Middleware）的作用是什么？你们用了哪些中间件？

**参考回答：**
中间件是在请求到达路由处理函数之前（或之后）执行的拦截器，适合做横切关注点的处理。我们用了两个请求中间件：

1. **`attach_request_id`**：为每个请求生成一个唯一的请求 ID（格式 `req_` + UUID 前12位），如果客户端提供了 `X-Request-Id` 请求头则复用。这个 ID 用于日志追踪和错误排查，贯穿整个请求的处理链。

2. **`check_api_key`**：API Key 认证中间件。如果配置了 `PYMS_API_KEY`，所有 `/v1/` 路径的请求都需要提供正确的 API Key。支持三种传递方式：Authorization Bearer Token、X-API-Key 请求头、URL 参数。

静态文件路径（`/` 和 `/static/`）和非 `/v1/` 路径不经过认证中间件。

### Q22: `PRAGMA foreign_keys = ON` 是什么意思？为什么要加？

**参考回答：**
SQLite 默认不启用外键约束，即使你在建表时定义了 `FOREIGN KEY`，SQLite 也不会实际检查引用完整性。`PRAGMA foreign_keys = ON` 是 SQLite 的一个编译指令，用于开启外键约束检查。

我们在每次获取数据库连接时都执行这个指令，确保：
- 不能向 `queue_items` 表插入一个不存在的 `task_id`
- 删除 `tasks` 表中的记录时，`ON DELETE CASCADE` 会自动删除关联的 `queue_items`、`event_logs`、`raw_items`、`clean_items` 记录

这样就保证了数据的引用完整性，防止出现孤立记录。

### Q23: 你们是怎么实现数据导出的？JSON 和 CSV 有什么区别？

**参考回答：**
数据导出功能在 `cleaning.py` 的 `export_results()` 函数中实现。

**JSON 导出：** 使用 `json.dumps()` 将清洗后的数据序列化为 JSON 字符串，`ensure_ascii=False` 保证中文正常显示，`indent=2` 美化输出。返回 `application/json` 类型的响应。

**CSV 导出：** 使用 Python 标准库的 `csv.DictWriter`，指定字段列表，写入 `io.StringIO` 缓冲区，最后编码为 UTF-8 字节。返回 `text/csv` 类型的响应。

两种格式都通过 `Content-Disposition: attachment` 头触发浏览器下载，文件名格式为 `{task_id}_results.{json|csv}`。前端通过创建 Blob 对象和临时 `<a>` 标签实现文件下载。

### Q24: `shlex.split()` 在命令引擎中起什么作用？

**参考回答：**
`shlex.split()` 是 Python 标准库提供的 Shell 词法分析器，它按照 Shell 的规则将命令字符串拆分为 token 列表。使用它的好处是：

1. **自动处理引号：** 如果 URL 中包含空格，可以用引号包裹，如 `url="https://example.com/path with spaces"`，`shlex.split()` 会正确解析为一个完整的 token。

2. **处理特殊字符：** 正确处理转义字符、引号嵌套等情况。

3. **安全：** 比手动用 `split(" ")` 更健壮，避免了因空格导致的参数解析错误。

解析后的 token 列表中，前两个元素是命令和子命令（如 `crawl` + `start`），后面的 `key=value` 格式的参数由 `_parse_params()` 函数进一步解析为字典。

### Q25: 请解释一下 `dataclass` 的作用和你们项目中的使用场景。

**参考回答：**
`dataclass` 是 Python 3.7 引入的装饰器，用于自动生成类的 `__init__`、`__repr__`、`__eq__` 等方法，减少样板代码。

项目中的使用场景：

1. **`Settings`（config.py）**：存储配置信息的 4 个字段，使用 `dataclass` 可以直接用 `settings.host` 方式访问。

2. **`TaskRecord`（service.py）**：任务记录的 14 个字段，除了自动生成的方法，还定义了 `progress` 计算属性。使用 `asdict()` 可以方便地转换为字典用于 JSON 序列化。

3. **`RawItem`（cleaning.py）**：原始爬取数据的 6 个字段，作为爬虫模块和清洗模块之间的数据传输对象。

4. **`CrawlResult`（worker.py）**：爬取结果的 4 个字段，用于在 fetch 函数和处理逻辑之间传递数据。

相比普通的 dict，`dataclass` 提供了类型提示、属性访问和更好的代码可读性。

### Q26: 爬虫的 User-Agent 为什么要伪装成 Chrome？

**参考回答：**
很多网站会检查请求的 User-Agent 头来识别客户端类型。如果 User-Agent 是 Python-requests 之类的爬虫标识，网站可能会拒绝请求或返回不同的内容（比如验证码页面）。

我们设置了 Chrome 浏览器的 User-Agent 字符串，同时设置了 Accept、Accept-Language、Connection 等请求头，让请求看起来更像是正常的浏览器访问。这是一种基本的反反爬策略，虽然简单但对很多没有高级反爬机制的网站是有效的。

### Q27: `threading.Event` 在 Worker 中是怎么用的？

**参考回答：**
`threading.Event` 是一个线程间的信号通知机制。我们在 `QueueRunner` 中使用了两个 Event：

1. **`_wake`（唤醒信号）：** 当没有待处理的队列项时，Worker 线程会调用 `self._wake.wait(POLL_INTERVAL)` 阻塞等待（默认 0.1 秒），而不是忙等待（不断循环查询数据库）。当有新任务提交或任务恢复时，调用 `notify()` 设置唤醒信号，Worker 线程立即被唤醒开始处理。

2. **`_stop`（停止信号）：** 用于优雅关闭 Worker。调用 `shutdown()` 时设置停止信号，Worker 线程的主循环检查到信号后退出。

这种设计避免了两种问题：一是忙等待浪费 CPU 资源，二是 Worker 不能及时响应新任务。

### Q28: 你们项目的响应格式是怎样的？

**参考回答：**
所有 API 返回统一的 JSON 格式：

```json
{
    "code": 0,           // 0=成功, 非0=错误码
    "message": "ok",     // 结果描述
    "request_id": "req_xxx",  // 请求追踪ID
    "data": { ... }      // 业务数据（成功时）或 null（失败时）
}
```

错误码的 HTTP 状态码映射：
- 1xxx 错误 → 400 Bad Request
- 1004 → 401 Unauthorized
- 2001 → 404 Not Found
- 2002 → 400 Bad Request
- 3xxx/5xxx → 500 Internal Server Error

这种统一格式的好处是前端可以统一处理响应，根据 `code` 判断成功或失败，`request_id` 便于后端日志追踪。

### Q29: `ThreadPoolExecutor` 和 `ProcessPoolExecutor` 有什么区别？为什么选线程池？

**参考回答：**
`ThreadPoolExecutor` 使用线程，`ProcessPoolExecutor` 使用进程。

选择线程池的原因：我们的爬虫任务是 I/O 密集型的（大部分时间在等待网络响应），而不是 CPU 密集型。Python 的 GIL（全局解释器锁）会限制 CPU 密集型任务的多线程性能，但对于 I/O 等待期间，GIL 会被释放，所以多线程仍然能有效提升并发性能。

如果是 CPU 密集型任务（比如大量数学计算），应该用 `ProcessPoolExecutor` 来绕过 GIL 限制。我们设置最大 4 个工作线程，既能保证一定的并发度，又不会对目标网站造成过大压力。

### Q30: 你们项目中有哪些设计模式的体现？

**参考回答：**

1. **状态模式（State Pattern）：** `state_machine.py` 中的状态机，每个状态定义了允许的转换，行为随状态变化。

2. **观察者模式（Observer Pattern）：** SSE 事件流，前端作为观察者订阅服务器端的事件推送。

3. **依赖注入（Dependency Injection）：** `set_fetcher()` 函数允许注入自定义的抓取函数，方便测试时模拟网络请求。

4. **中间件模式（Middleware Pattern）：** Sanic 的请求中间件，在请求处理前后执行通用逻辑。

5. **命令模式（Command Pattern）：** 命令引擎将命令字符串解析为可执行的操作，每种命令对应一个处理函数。

6. **数据传输对象（DTO）：** `RawItem`、`CrawlResult`、`TaskRecord` 等 `dataclass` 作为模块间的数据传输载体。

7. **模板方法模式：** 前端的一键执行流程定义了固定的操作步骤（提交→爬取→清洗→分析），具体实现由各步骤的 API 调用完成。
