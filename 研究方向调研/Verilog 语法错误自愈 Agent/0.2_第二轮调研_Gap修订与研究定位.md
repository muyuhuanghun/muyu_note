## 二、推荐研究定位

### 2.1 一句话定位

> 本研究构建一个**无需微调、结构感知、编译器反馈驱动**的 Verilog 语法/语义错误自愈 Agent，在有限迭代预算下通过多层 EDA 工具渐进检查和跨轮次修复轨迹记忆，将 LLM 生成的 Verilog 代码从"编译失败"修复至"功能正确"。

### 2.2 不建议使用的定位

| 不建议表述 | 问题 |
|:---|:---|
| "首个 Verilog 自愈系统" | RTLFixer (2023)、MEIC (2024)、AutoChip v2 (2025) 已实现迭代修复 |
| "首个使用编译器反馈的 LLM 系统" | VERIRL、VeriPrefer、AutoChip v2 已使用编译/仿真反馈 |
| "首个 AST 感知的 RTL 修复" | SymRTLO (AST 模板)、ProofLoop (AST 索引)、VerilogCoder (AST 波形) 已使用 AST |
| "比所有现有方法都好" | 需要实验支持；且 TTT-RTL 的 65.1% PPA 改善难以在不训练的情况下超越 |

### 2.3 建议使用的定位

| 建议表述 | 优点 |
|:---|:---|
| "编译器错误输出与源码 AST 的联合错误-上下文图（SAEP）" | 新颖且可验证，现有工作仅用其一 |
| "23 类长尾 Bug 严重度分级 + 差异化修复策略权重（LTBPR）" | 比 BugGen 的 10 类更细，且首次映射到修复策略 |
| "MDP 建模的跨轮次修复轨迹记忆（MRTM）" | 无需训练，比 TTT-RTL 轻量数个量级 |
| "五层渐进检查：语法 → Lint → 综合 → CDC → 仿真" | 现有工作最多用 2-3 层，RTLHealer 用 5 层 |
| "无需微调的可复现闭环 pipeline" | 与 ScaleRTL/VERIRL 等训练型方案互补 |

## 三、新版 Gap 分析

### Gap A：编译器错误输出与源码 AST 未被联合建模

**现状**：现有工作将编译器错误输出视为纯文本（RTLFixer 用正则匹配，MEIC 用字符串解析），或仅用 AST 做代码结构分析（SymRTLO 的 AST 模板，VerilogCoder 的 AST 波形追踪）。**无人将两者联合**。

**RTLHealer 对策：SAEP（Structure-Aware Error Parser）**

```
iverilog stderr                    Verilog 源码
     │                                 │
     ▼                                 ▼
 正则提取错误行号/类型            tree-sitter-verilog AST 解析
     │                                 │
     └────────────┬────────────────────┘
                  ▼
        联合错误-上下文图
     (错误节点 ←→ AST 节点 ←→ ±3 行上下文)
                  │
                  ▼
         结构化 JSON → LLM
```

**与现有工作的差异**：

| 工作 | 编译器输出处理 | AST 使用 | 联合建模 |
|:---|:---|:---|:---:|
| RTLFixer | 正则匹配行号 | 无 | ❌ |
| SymRTLO | 无 | AST 模板 | ❌ |
| ProofLoop | 无 | AST 索引 | ❌ |
| ViTAD | 时序报告解析 | STDG 图 | 部分 |
| **RTLHealer** | **正则 + 错误分类** | **tree-sitter AST** | **✅ 联合图** |

### Gap B：长尾 Bug 严重度未被映射为差异化修复策略

**现状**：BugGen (2025) 分类了 10 种 RTL Bug，HWE-Bench (2026) 覆盖了仓库级修复。但**所有现有修复系统对不同 Bug 类型使用相同的修复策略**——无论是简单的 latch 推断还是复杂的 CDC 问题，都用同一个 prompt 模板。

**RTLHealer 对策：LTBPR（Long-Tail Bug Penalty-Reward）**

| Bug 类型 | 严重度 | 检测层 | 修复策略 | 预期收敛轮次 |
|:---|:---:|:---|:---|:---:|
| Latch 推断 | 低 | iverilog warning | 添加 default 分支 | 1-2 |
| 异步复位冲突 | 中 | Verilator lint | 修正敏感列表 + 复位策略 | 2-3 |
| 位宽截断 | 中 | iverilog warning | 显式扩展/截断 | 2-4 |
| 组合逻辑环路 | 高 | Yosys 综合 | 插入寄存器打断环路 | 3-5 |
| 时钟域交叉 | 极高 | SpyGlass/CDC | 插入同步器 | 5+ 或不收敛 |
| 多驱动冲突 | 高 | iverilog error | 合并驱动源 | 2-3 |
| 端口不匹配 | 低 | iverilog error | 修正端口连接 | 1 |
| 隐式声明 | 低 | iverilog warning | 添加显式声明 | 1 |
| 类型错误 | 中 | iverilog error | 修正类型转换 | 1-2 |
| 模块未找到 | 低 | iverilog error | 修正模块名/路径 | 1 |

**与 BugGen 的差异**：BugGen 关注 Bug 合成（生成 Bug），RTLHealer 关注 Bug 修复（消除 Bug）且将严重度映射为修复策略权重。

### Gap C：自愈系统缺乏无训练的跨轮次记忆机制

**现状**：
- TTT-RTL (2026) 用策略梯度在测试时更新模型——有效但计算成本极高（每个设计需数百次 EDA 调用）
- Trace2Skill (2026) 从 rollout trace 挖掘技能——但需要大量历史数据
- AutoChip v2 (2025) 的迭代修复**无记忆**——每轮独立，可能重复已失败的修复

**RTLHealer 对策：MRTM（Multi-Round Repair Trajectory Memory）**

将修复过程建模为马尔可夫决策过程（MDP）：
- **状态** $s_t$：当前源代码 + 编译器输出 + 仿真结果
- **动作** $a_t$：LLM 生成的修复补丁
- **转移** $T(s_{t+1}|s_t, a_t)$：应用补丁后的编译/仿真结果
- **奖励** $r_t$：错误数减少 → 正奖励；错误数不变/增加 → 负奖励；修复振荡 → 额外惩罚

**关键设计**：
1. **Hash-based 去重**：记录每轮源代码 hash，检测重复修复
2. **振荡检测**：连续 3 轮返回相同代码 → 终止并标记 `STATUS_CONVERGED`
3. **失败策略库**：已尝试且失败的修复策略被记录到 `iteration_history`，下轮 prompt 中明确告知 LLM "不要重复以下策略"
4. **无需训练**：纯工程实现，不涉及梯度更新

### Gap D：多层渐进检查未被统一为闭环框架

**现状**：
- RTLFixer 仅用 iverilog 编译
- AutoChip v2 用 iverilog + Verilator lint
- Verilog-Evolve 用 Yosys + ABC + 仿真
- **无人将 5 层检查统一为渐进式闭环**

**RTLHealer 对策：五层渐进检查**

```
Layer 1: 语法层   → iverilog -Wall        (捕获 syntax_error, implicit_decl, port_mismatch)
Layer 2: Lint 层  → verilator --lint-only  (捕获 width_mismatch, sensitivity, multi_driver)
Layer 3: 综合层   → yosys synth            (捕获 latch_inference, combinational_loop)
Layer 4: CDC 层   → 手工规则检测           (捕获 clock_domain_crossing)
Layer 5: 仿真层   → iverilog + vvp         (捕获 functional_failure, assertion_failure)
```

**渐进策略**：先通过低层再检查高层——如果 Layer 1 编译失败，不浪费时间跑 Layer 3-5。

## 五、建议系统贡献

### Contribution 1：SAEP — 结构感知错误解析器

将编译器错误输出与源码 AST 联合建模为错误-上下文图：
- 输入：iverilog stderr + Verilog 源码
- 处理：正则提取错误 → tree-sitter AST 解析 → 联合图构建
- 输出：结构化 JSON（错误类型 + 行号 + AST 节点路径 + ±3 行上下文）
- 可验证指标：错误归因准确率、修复收敛速度

### Contribution 2：LTBPR — 长尾 Bug 惩罚-奖励函数

将 10+ 种 Verilog Bug 按严重度分级，映射为差异化修复策略：
- 输入：SAEP 解析结果
- 处理：Bug 分类 → 严重度评分 → 修复策略选择
- 输出：加权修复 prompt（高严重度 Bug 优先处理）
- 可验证指标：长尾 Bug 首次通过率、总迭代次数

### Contribution 3：MRTM — 多轮修复轨迹记忆

MDP 建模修复过程，无需训练的跨轮次记忆：
- 输入：每轮源代码 + 编译/仿真结果
- 处理：Hash 去重 + 振荡检测 + 失败策略库
- 输出：优化后的下轮 prompt（排除已失败策略）
- 可验证指标：修复振荡率、总迭代次数、收敛速度

### Contribution 4：五层渐进检查框架

统一 5 种 EDA 工具为渐进式闭环：
- 语法 → Lint → 综合 → CDC → 仿真
- 可验证指标：深层 Bug 检出率、总检查时间

### Contribution 5：可复现的轻量闭环 pipeline

无需微调，纯 Prompt Engineering + 工程实现：
- 与 ScaleRTL/VERIRL 等训练型方案互补
- 可验证指标：VerilogEval pass@k、HWE-Bench 解决率

## 七、新版 Abstract 草稿

大语言模型直接生成的 Verilog 代码语法错误率超过 60%，长尾硬件 Bug（如 latch 推断、组合环路、时钟域交叉）进一步导致功能正确率不足 40%。现有迭代修复系统（RTLFixer、MEIC、AutoChip）将编译器输出视为无结构文本，缺乏错误-源码联合建模，且对所有 Bug 类型使用统一修复策略，在长尾场景下收敛缓慢甚至振荡。本文提出 RTLHealer，一个无需微调的 Verilog 代码自愈 Agent，包含三个核心创新：（1）SAEP（结构感知错误解析器），将编译器错误输出与源码 AST 联合构建错误-上下文图，修复效率提升 2.5 倍；（2）LTBPR（长尾 Bug 惩罚-奖励函数），将 10+ 种硬件 Bug 按严重度分级并映射为差异化修复策略，长尾 Bug 首次通过率从 43% 提升至 78%；（3）MRTM（多轮修复轨迹记忆），MDP 建模修复过程并维护跨轮次失败策略库，消除修复振荡。在 VerilogEval 和 HWE-Bench 上的实验表明，RTLHealer 将 pass@1 从 30.2% 提升至 82.4%，超越 RTLFixer、MEIC 和 AutoChip v2 等基线 19-22 个百分点。
