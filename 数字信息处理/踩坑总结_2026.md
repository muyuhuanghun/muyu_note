## 先说结论

这次排查里，有一个已经从代码和运行现象两边确认的故障: UART 只能发送 `HELLO!`、不能回显，是因为程序只打开了 USCI_A0 接收中断，没有打开 CPU 的全局中断 GIE。补上 `__enable_interrupt()` 后，回显成功。

板卡识别问题没有得到同样强度的闭环证据。已有事实能说明板子、目标 MCU 和板载 eZ-FET 至少成功工作过，因为 CCS GUI 曾经完成下载和调试，串口也输出过 `HELLO!`。但是，`DSLite` 的报错、CCS GUI 的报错、拔 USB 后的异常，以及两个不同位置的 `launch.json`，目前还不能被压缩成一个已经证明的唯一根因。最合理的说法是: 工程和工作区配置混乱与故障高度相关，拔线时仍处于调试会话也增加了异常风险，最终还需要一次干净重启后的 GUI 复测来收口。

因此，当前状态是:

- 实验 1 的 UART 发送和回显曾经跑通。
- UART 中断代码已经修正，当前源码中保留了修复。
- CCS 工程的器件和目标配置文件存在，内容指向 MSP430G2553 和 `TI MSP430 USB1`。
- 会话记录称多余的 `launch.json` 配置已经删除。当前磁盘上的每个 `launch.json` 都只剩一条配置。
- 工作区里仍有两个不同位置的 `.theia/launch.json`，而且 `resourceId` 不同。今后必须固定工程打开方式，避免 CCS 读取另一份启动配置。
- 拔插 USB 后的 CCS GUI 是否已经恢复，仍等最终复测。不能提前写成"已恢复正常"。

## 问题 1: CCS 一度识别不到板子

### 现象

会话中出现过两类提示:

- `No compatible board detected - please connect your board`
- `Could not find MSP-FET430UIF on specified COM port`

设备管理器当时能看到 `MSP430 Application UART (COM9)`，说明回传串口枚举出来了。另一个 USB 接口表现为 HID，由此产生了"调试接口被 HID 驱动占用"的判断。

### 当时哪里判断错了

最大的问题不是某一个命令输错，而是诊断顺序反了。我们在没有先问清"这块板子之前是否成功调试过"的情况下，就开始找旧驱动、换 CCS 版本、怀疑板子。

后来用户补充，CCS GUI 之前已经成功下载并运行程序，串口收到过 `HELLO!`。这条证据至少说明:

- MSP430G2553 能运行下载进去的程序。
- 板载 eZ-FET 至少成功建立过下载或调试连接。
- USB 线、电源和目标板不是"完全不可用"。

它不能证明每次重插都一定正常，也不能直接解释 DSLite 为什么失败。

### 现在能确认什么

TI 的 MSP-EXP430G2ET 用户指南说明，这块板上有板载 eZ-FET，eZ-FET 同时提供 Spy-Bi-Wire 调试和 USB 回传 UART。主机侧会出现一个供终端软件使用的虚拟 COM 口。也就是说，"Application UART 的 COM 口"和"CCS 使用的调试连接"本来就是两条不同用途的通道。

当前工程的配置也与这套硬件对应:

- `.ccsproject` 的器件是 `MSP430G2553`。
- 连接是 `common/targetdb/connections/TIMSP430-USB.xml`。
- 活动目标配置是 `targetConfigs/MSP430G2553.ccxml`。
- `.ccxml` 中的连接是 `TI MSP430 USB1`，目标器件是 `MSP430G2553`。

### 正确处理方式

先用 CCS GUI 对当前工程做一次干净复测，再决定要不要继续查驱动:

1. 关闭所有 CCS 窗口，确认没有残留调试会话。
2. 重新插入开发板，等设备管理器枚举稳定。
3. 固定一种工程打开方式，不要在外层目录和实际工程目录之间来回切换。
4. 在 CCS 中确认选中的是包含 `.ccsproject` 的 UART 工程。
5. 确认活动目标配置为 `targetConfigs/MSP430G2553.ccxml`。
6. 从 GUI 启动 `Debug Project`，保存 Output 面板的完整日志。
7. 如果仍失败，再根据同一次复测的日志定位，不要先装第三个 CCS 或强制替换驱动。

## 问题 2: 把 HID 接口当成了"错误驱动占用"

### 当时的误判

看到 USB 设备的一个接口由 HID 驱动管理后，我们把它理解成"调试接口本该是 COM 口，只是被 Windows 占走了"，随后尝试让 `usbuart3410.inf` 匹配该接口。

这个推理跳过了板卡型号和接口用途。MSP-EXP430G2ET 使用板载 eZ-FET，UART 回传会单独生成虚拟 COM 口。不能因为调试侧没有第二个 COM 口，就断定驱动错误。

### 这次应该保留的结论

- `COM9` 是当时的 Application UART 端口号。端口号换电脑或重插后可能变化。
- UART 端口能出现，只证明 UART 回传接口枚举成功，不等于 CCS 调试连接一定成功。
- 不能只凭 `PID_F432` 或 HID 外观，就手动把老式 `usbuart3410.inf` 套到这个接口上。
- TI 说明 CCS 或 IAR 会附带所需的 MSP Debug Stack 低层驱动。只有脱离 IDE 单独使用开放调试栈或烧录器时，才需要按对应工具说明另装驱动。

这份记录不再保留"F432 一定不需要任何驱动"这样的绝对说法。更准确的说法是: 不应该在没有硬件 ID 匹配和工具文档支持的情况下，强行安装旧驱动；正常的 CCS 安装应当带上它需要的调试支持。

## 问题 3: 把 DSLite 报错当成整套 CCS 不可用

### 现象

DSLite 返回了 `Could not find MSP-FET430UIF on specified COM port`。随后安装 CCS 21.0.1，同类错误仍然出现。

### 当时的错误推理

我们一度把这条命令行错误解释成:

- CCS 不支持这块板。
- 板载 eZ-FET 已损坏。
- DSLite 固定在寻找老式 F430 设备。

前两项被后来 GUI 成功运行的事实削弱。第三项在现有本地日志和官方资料里没有得到证明，因此不能再写成"固定 bug"或"真实原因"。

### 正确理解

DSLite 的失败只说明那一次命令行连接没有建立。它可能涉及目标配置、启动上下文、探针选择、驱动栈或工具参数，但必须看完整命令和完整日志才能区分。

CCS Theia 官方文档明确区分了目标配置文件和启动配置。GUI 会读取 `.ccxml`，再结合 `launch.json` 建立调试会话。命令行和 GUI 是否使用了完全相同的目标配置，必须实际核对，不能凭报错文本猜。

### 以后怎么查

如果需要继续分析 DSLite，至少保存以下材料:

- 完整命令行，不省略参数。
- 完整标准输出和错误输出。
- 实际传入的 `.ccxml` 绝对路径及文件哈希。
- 同一时间 CCS GUI 使用的活动目标配置。
- 设备管理器中的硬件 ID 和驱动程序详细信息。

没有这些材料时，只能记录"DSLite 失败，GUI 曾成功"，不能继续编造二者差异的原因。

安装 CCS 21.0.1 没有消除报错。这一步没有提供能区分"版本问题"和"配置问题"的对照证据，还增加了这些风险:

- 编译器、调试栈和目标数据库版本混用。
- 后续日志难以判断来自哪一套安装。

当前 UART 工程生成的构建文件指向 `C:/ti/ccstheia151`，说明该工程至少曾由 CCS Theia 1.5.1 的工具链构建。

是否卸载 CCS 21.0.1 不应在这份总结里直接下命令。先确认现在实际使用哪套 CCS、哪套工具链，以及是否有其他工程依赖 21.0.1。确认没有依赖后，再由用户决定是否卸载。

## 问题 6: UART 能发 `HELLO!`，却不能回显

这是本次证据最完整的问题。

### 现象

板子周期发送 `HELLO!\r\n`，SSCOM 能收到。PC 发送字符后，板子没有回传。

发送功能正常，说明 DCO、UART 引脚复用、波特率和发送寄存器至少基本可用。故障集中在接收中断路径。

### 根因

原代码打开了 USCI_A0 的接收中断:

```c
IE2 |= UCA0RXIE;
```

但 CPU 状态寄存器中的全局中断位 GIE 没有打开。原 TI 例程通过下面这行同时进入 LPM0 并打开 GIE:

```c
__bis_SR_register(LPM0_bits + GIE);
```

改写程序时，这行被注释，发送逻辑改成了循环查询，但没有把 GIE 单独补回来。于是外设可以提出中断请求，CPU 却不会进入 `USCI0RX_ISR`。

### 修复

当前源码在打开接收中断后紧接着执行:

```c
IE2 |= UCA0RXIE;
__enable_interrupt();
```

接收中断函数仍然是:

```c
#pragma vector=USCIAB0RX_VECTOR
__interrupt void USCI0RX_ISR(void)
{
    while (!(IFG2 & UCA0TXIFG));
    UCA0TXBUF = UCA0RXBUF;
}
```

会话记录显示，补上 GIE 后，发送字符 `A` 能收到 `A` 回显。这个结果与代码改动吻合。

### 这里真正学到的东西

MSP430 的中断路径至少要同时满足:

1. 外设模块允许产生该类中断，例如 `IE2 |= UCA0RXIE`。
2. CPU 允许响应可屏蔽中断，例如 `__enable_interrupt()` 或设置 `GIE`。
3. 中断向量和 ISR 声明正确。
4. 外设已经退出复位状态，相关引脚和时钟已经配置。

这次缺的是第 2 项。以后从 TI 低功耗例程改成普通循环时，要把"进入低功耗"和"打开全局中断"拆开检查，不能把两件事一起删掉。

## 问题 7: 调试过程中直接拔 USB，重插后 GUI 也报错

### 已知事实

- 第一次 GUI 调试和 UART 回显成功后，USB 被拔出。
- 当时没有先结束调试会话。
- 重插后，CCS GUI 出现 `MSP-FET430UIF` 相关错误。
- 会话记录称 `launch.json` 中曾出现第二条带 `(1)` 的配置，随后将其删除。

TI 的 MSP Debug Stack 页面明确提醒，不要在活动调试会话中拔掉 JTAG 或调试连接，因为这可能让目标处于未知状态。这里可以确定的是操作顺序不安全。

### 不能过度下结论的地方

现有目录没有保留修改前的 `launch.json`、CCS Output 日志或文件时间线。因此，"直接拔线必然写坏 `launch.json`"还只是推断。可能同时存在的因素包括:

- CCS 仍保存着失效的调试会话。
- USB 设备重枚举后，旧连接未释放。
- 工程从不同目录层级打开，CCS 读取了另一份 `.theia/launch.json`。
- 多个启动配置中选中了错误项。
- 目标配置或探针选择与上一次不同。

### 当前磁盘上更值得注意的问题

现在有两份启动文件:

1. `documents/msp430g2xx3_uscia0_uart_01_115k/.theia/launch.json`
2. `documents/msp430g2xx3_uscia0_uart_01_115k/msp430g2xx3_uscia0_uart_01_115k/.theia/launch.json`

两份文件都只有一条配置，但 `resourceId` 不同:

```text
/msp430g2xx3_uscia0_uart_01_115k
/msp430g2xx3_uscia0_uart_01_115k/targetConfigs
```

CCS Theia 官方文档说明，`launch.json` 位于工作区的 `.theia` 目录中。因此，打开外层目录还是内层工程目录，可能让 CCS 使用不同的启动文件。下一次复测前应先固定工作区根目录，并从 CCS Debug 视图确认实际选中的启动配置。

### 标准拔线顺序

1. 在 CCS Debug 视图中点击 Terminate。
2. 等待调用栈和调试会话从界面中消失。
3. 如准备关闭 CCS，正常退出并等进程结束。
4. 再拔 USB。

如果只是改代码后重新烧录，通常不需要拔 USB。结束旧会话、重新构建并启动调试即可。

## 问题 7 的实测补充: 按 CCS 提示直接拔插 USB 就是答案

### 现象
再次进入 Debug 时，CCS Theia GUI 弹出:

```
MSP430G2553 Unable to connect to MSP430G2553.
Please unplug and re-plug the USB connection and try again.
TI MSP430 USB1/MSP430 Error initializing emulator:
Could not find MSP-FET430UIF on specified COM port
```

用户**按 CCS 自己的提示直接拔插 USB，没有再清任何缓存、没有再改任何配置**，重试后烧录成功。

### 这条新证据改变了什么
- 之前的建议 (清 `.lock`、清 `.theia`、清 `ccs2101` 工作区) 都是**过头动作**。这次能成功恰恰说明工程配置没问题。
- CCS 弹这条错误时，它**没有要求清理任何缓存**——它自己提示的就是拔插 USB。
- 报错文本里的"MSP-FET430UIF on COM port" 仍然可能是误导性文本，不一定反映真实探测逻辑。

### 现在的标准操作
再遇到这条错误，按以下顺序处理，**先别动文件**:

1. 看 CCS 弹出的提示。如果提示是"unplug and re-plug the USB connection"，**就按它说的做**。
2. 完全退出当前 Debug 会话 (Terminate, 不是 Disconnect)。
3. 拔 USB，等 3~5 秒。
4. 重新插 USB，等设备管理器把 `MSP430 Application UART` 和 HID 设备都枚举成 OK。
5. 在 CCS 里**直接重试 Debug**，不要重开 CCS。
6. 如果还是失败，再考虑这次复现的 Output 日志，再决定要不要清缓存。

### 什么情况下才去清缓存
- 同一份日志里**明确出现文件路径**、缓存路径或 `cinit` 相关报错。
- 连续两次拔插 USB 都报同一错。
- Output 面板显示 `Initializing` 阶段就卡死、不进入 `Initializing: MSP430`。

只在上面这些情况下，再按"问题 7"里写的顺序清理。**别把清理缓存当成默认修复**。

## 问题 8: `Initializing: MSP430` 很慢

### 现象

会话记录称，`Configuring Debugger ... Initializing: MSP430` 有时持续 1 到 3 分钟，尤其是在拔插 USB 或重新启动 CCS 后。

### 原总结哪里写过头了

旧总结把耗时直接归因于:

- `msp430_emu.dvr` 被 Defender 扫描。
- `targetdb` 中大量 XML 首次解析。
- eZ-FET 握手。
- 拔 USB 导致缓存失效。

这些机制都可能参与启动，但当前没有性能日志、进程跟踪或 A/B 测试，不能说哪一项是主因，也不能把"1 到 2 分钟正常、5 分钟以上异常"当成已经验证的阈值。

### 更可靠的排查方法

1. 记录每次启动的开始时间、结束时间和是否刚拔插 USB。
2. 区分构建耗时、连接探针耗时、下载程序耗时和运行到 `main()` 的耗时。
3. 保存 CCS Output 面板日志，找出实际停在哪一步。
4. 连续启动两次，不拔 USB，比较冷启动和热启动。
5. 检查 CCS 进程是否仍在后台占用旧会话。
6. 只有在日志显示文件扫描或安全软件明显占用时，才做受控的 Defender 排除项测试。测试前后要记录耗时，没有改善就撤销。

"不要频繁拔 USB"和"保持同一个工作区"仍是低成本、可复现的做法。Defender 排除项不能被当成默认修复。

## 问题 9: 修完文件就提前宣布"全部通过"

旧总结最后写了"CCS Theia GUI 正常 debug"和"可以进阶段 2"，但同一份会话记录又写着"现在等用户测试"。这两个状态互相矛盾。

正确的状态拆分应该是:

| 项目 | 证据 | 当前结论 |
| --- | --- | --- |
| UART 周期发送 `HELLO!` | 用户运行观察 | 曾经通过 |
| 字符回显 | 加 GIE 后的用户运行观察 | 曾经通过 |
| 源码保留 GIE 修复 | 当前源码 | 已确认 |
| 多余的 `(1)` 启动项已删除 | 会话记录；当前每份文件仅一条配置 | 文件层面已清理 |
| 拔插 USB 后 GUI 能重新 Debug | 尚无最终复测结果 | 待确认 |
| 阶段 1 正式验收完成 | 实验 README 仍未勾选，且 GUI 恢复待确认 | 尚未正式关闭 |

这个区别很重要。改了配置只能写"已修改"；成功启动一次才能写"本次复测通过"；要关闭阶段，还要把验收项和证据一起更新。

## 推荐的复测记录

下一次测试只做一条干净路径，并把结果写下来:

| 步骤 | 操作 | 需要保存的证据 |
| --- | --- | --- |
| 1 | 完全退出 CCS，重新插板 | 设备管理器截图，包含 Application UART 和相关 USB 接口 |
| 2 | 打开固定的工作区和 UART 工程 | CCS 标题栏或 Explorer 截图，能看出工程路径 |
| 3 | 检查活动 `.ccxml` | Target Configuration 视图截图 |
| 4 | 启动 GUI Debug | Output 面板从启动到进入 `main()` 的完整文本 |
| 5 | Continue 运行 | SSCOM 收到 `HELLO!` 的截图 |
| 6 | SSCOM 发送 `A` | 发送和接收都显示 `A` 的截图 |
| 7 | Terminate | Debug 会话消失的截图或记录 |
| 8 | 不拔 USB，再启动一次 Debug | 第二次启动耗时和结果 |

如果这 8 步全部通过，才把 `documents/实验1_UART/README.md` 的对应验收项勾上，并把本文件的"待确认"改成"本次复测通过"。

## 以后遇到同类问题的排查顺序

### CCS 连接或板卡识别

1. 先问清楚之前是否成功过，以及最后一次成功之后改了什么。
2. 确认板卡型号、目标 MCU、USB 接口用途和跳线状态。
3. 固定工作区和工程路径，核对 `.ccsproject` 与活动 `.ccxml`。
4. 用 CCS GUI 做最小复测并保存完整日志。
5. 再查设备管理器、驱动版本和硬件 ID。
6. 最后才考虑换 CCS 版本、重装驱动或怀疑硬件损坏。

### MSP430 中断不响应

1. 看中断允许位。
2. 看 GIE。
3. 看中断向量和 ISR。
4. 看中断标志是否产生、是否被意外清除。
5. 看外设时钟、引脚复用和复位状态。
6. 用断点、GPIO 翻转或计数器证明 ISR 到底有没有进入。

### USB 断开和重连

1. 先 Terminate。
2. 不需要拔线时就不拔。
3. 重连后等枚举稳定。
4. 清理配置前先备份原文件和 Output 日志。
5. 改完配置后必须做一次新的运行验证。

## 最终经验

这次最值得保留的不是"某个版本好不好用"，而是证据顺序。成功运行过的现象，可以排除一批硬件层面的绝对故障；一条命令行报错，只能说明那次命令失败；改完配置，也只能说明文件变了。每一步都写清"观察到了什么、因此能排除什么、还不能证明什么"，排查会快很多，复盘也不会自相矛盾。
